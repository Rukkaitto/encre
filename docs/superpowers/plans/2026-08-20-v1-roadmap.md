# E-Reader Firmware V1 — Implementation Roadmap

> **For agentic workers:** This is the phase index, not an executable plan.
> Each phase below gets its own bite-sized plan in `docs/superpowers/plans/`
> when its turn comes (Phase 1's already exists). Execute phases in order —
> each one ends with working, testable software.

**Spec:** `docs/superpowers/specs/2026-08-20-ereader-firmware-v1-design.md`
**Design canvas:** the "E-Reader V1 UI" artifact (47 boards; V1 Screens +
Flows & States pages are the visual contract, theme B2 "Quiet").

## Ground rules for every phase

- The portable core (`core/`) never includes Arduino headers. It builds on
  macOS via CMake and is covered by doctest unit tests + golden-PNG
  visual-regression tests through the simulator.
- Themes render view-models; screens never draw pixels directly (spec §3.3).
- TDD, bite-sized tasks, frequent commits. Firmware builds via PlatformIO
  `[env:xteink]` (one binary, X3+X4).

## Phases

### Phase 1 — Foundation (plan: `2026-08-20-phase1-foundation.md`)
Repo scaffold, freeink-sdk submodule, desktop test harness, 1-bit
framebuffer, bitmap font pipeline (converter + loader + text rendering),
view-model/theme skeleton with a first QuietTheme Home, simulator CLI
rendering PNGs, and firmware that boots on the X4 and shows that Home.
**Exit:** `make test` green on macOS; a photo of the device showing the Home
screen render.

### Phase 2 — UI system & static screens

Split into three plans: the scope below is three independent subsystems with
different risk profiles, and each sub-phase produces working software on its own.

**2A — Design fidelity** — DONE (plan: `2026-08-20-phase2a-design-fidelity.md`)
Outcome: Home matches its board in the simulator on both geometries, and the
component vocabulary exists. Hardware verification failed on legibility, which
triggered the grayscale course correction below — that was the task working as
intended, not the phase failing.
The typography and drawing foundation everything else renders through: text
ink colour and letterspacing, a missing-glyph fallback, the multi-size type
ramp, canvas-agnostic layout, the QuietTheme component primitives (bands,
rows, hint bars, dither, icons), and Home at full design fidelity on both
panel geometries.
**Exit:** `make compare --only home` shows Home matching its board; goldens at
both 480×800 and 528×792; verified on X3 hardware.

**2A-2 — Grayscale text** — DONE (plan: `2026-08-20-phase2a2-grayscale-text.md`)
Outcome: chrome is legible on X3 hardware and Home matches its board. What it
took beyond the plan: the pt-at-150-DPI ramp (the original 12-24px ramp was
authored on a monitor and roughly half a legible size), icons generated from the
design's own SVGs, and eleven fidelity defects fixed in the shared primitives
rather than per-screen. The UC8279 grayscale driver — which the SDK documents as
never hardware-validated — works.
Chrome moves to the panel's 4-level path so small type is legible: 2bpp glyph
coverage, the screen drawn once per bit-plane, composed 4-level goldens.
**Exit:** chrome legible at 12-13px on X3 hardware, goldens re-blessed.

**2B — Interaction runtime** — DONE (plan: `2026-08-20-phase2b-interaction-runtime.md`)
Input dispatch with short/long press, the screen stack, focus navigation, the
e-ink refresh policy (FAST page turns, FULL every N turns and on transitions),
and the power manager with sleep/wake.
**Exit:** navigate between stub screens on device using the buttons; sleep and
wake cleanly.

What the phase settled beyond its own scope:
- **The runtime is logic, so it lives in `core/` and is unit-tested on the
  desktop.** The shell contributes only the three things that need hardware: raw
  button samples with timestamps, the panel refresh calls, and deep sleep.
- **The hint bar's hold ring and the long-press binding read one field**
  (`HomeViewModel::holds`, via `hintHoldMask`). A screen therefore cannot promise
  a hold it has not bound, or bind one with nothing on screen to suggest it.
- **One physical press is exactly one event.** A hold fires `Long` while the
  button is still down and the release then emits nothing; a button outside the
  mask fires `Short` on release however long it was held — never nothing.
- **Screens declare a `Fidelity`.** 2B had chrome on `Gray` because 1-bit
  *thresholded* chrome is illegible on this panel (2A-2). **Superseded within the
  phase** — see "Measured paint cost" below: 1-bit *dithered* chrome is legible,
  so the enum became `Dithered`/`Grayscale` with `Dithered` the default.
  **Superseded again (2026-08-21), and this time the other way** — see "Matching
  the reference firmware's chrome" below. The enum is now
  `Mono`/`Dithered`/`Grayscale`, **`Mono` is the default and what ships**, and the
  2A-2 measurement turns out to have been about the px-authored type ramp rather
  than about thresholding.
- **`InputManager::beginAsync()` cannot support a long press** — it queues press
  edges only, no releases and no durations. The shell runs its own poll task
  instead, queuing both edges with a `millis()` timestamp.
- **Deep sleep is a chip reset and only the power button can wake it.** The six
  front buttons are ADC-ladder bands on GPIO 1/2 and produce no GPIO edge; power
  is a real GPIO (3, active-LOW). So all RAM state is lost on wake.

**Measured paint cost — RESOLVED, and not the way this section predicted**
(X3, from a device log)

> The conclusion below — that the remaining lever was a **windowed grayscale
> update** — is superseded. It was investigated and rejected: **rotation is CCW**,
> so a portrait row band becomes a full-height landscape *column* band, and every
> gate line is driven whether the window is a strip or the whole frame. There is
> no partial-refresh win to have on a row-banded chrome change.
>
> The answer was to stop using the grayscale path at all. `Plane::BwDithered`
> keeps the anti-aliasing on a **single 1-bit pass** by stippling glyph and icon
> edge coverage through a dispersed Bayer 4×4 instead of thresholding it away, so
> chrome costs **one render pass and one waveform** in place of four passes and
> three (367 + 366 + 156 ms). A focus move went from the **1363 ms** measured
> below to a single FAST refresh. Verified on the X3: "Looks good and it's fast."
>
> What was wrong in the old reasoning was one word. 2A-2 measured 1-bit
> *thresholding* as illegible and the conclusion was recorded as "chrome needs
> grey", which is a stronger claim than the measurement supports — chrome needs
> *anti-aliasing*, and a 1-bit frame can carry it. The grayscale path is retained
> for Phase 3's question about book images, which is the one thing a stipple
> cannot do: continuous tone.
>
> `Fidelity` is now `Dithered`/`Grayscale` with `Dithered` the default, so nothing
> takes the expensive path without asking. The rest of this section stands as the
> measurement it was.

A chrome repaint cost ~1.9 s, and **a focus move and a screen push cost the same**
— 1924 ms vs 1840 ms. The felt difference was the opposite of the real one: the
paints that seemed *quicker* were the slowest (2.6 s), because they included the
693 ms full B/W `8279_DRF` that flashes the panel black, and that flash reads as
the device acknowledging the press. A grayscale-only update sits unchanged for
~1.9 s and then switches, with nothing in between. **On e-ink, feedback and speed
are separate problems** — worth remembering before optimising the wrong one.

Where the 1.9 s went, per `[paint] done total=1924ms render=885ms panel=1039ms`:

- **render 885 ms — mostly fixed.** 87% of it was `rotate90CCW`, per-pixel, run
  four times per paint and content-independent (which is why the two screens
  matched). Now a block transpose, 6.8× faster; expect render nearer 240 ms.
- **panel 1039 ms — untouched.** Three `8279_gray_DRF` waits (367 + 366 + 156)
  for the base frame, the settle pass and the combine. This is the remaining
  lever and it needs a **windowed grayscale update**: the log reports
  `strip=1`, so the driver supports strip grayscale, and a focus move only
  changes two row bands out of 792 rows. Same machinery Phase 3 needs for page
  turns, so it belongs there rather than being bolted on.
  — **REJECTED, see the note above.** The rotation is CCW: a portrait row band is
  a landscape column band, so a strip window drives every gate line regardless.
  Chrome left the grayscale path instead.
- A smaller win alongside it, **now moot for chrome** and only relevant if a
  Phase 3 screen declares `Grayscale`: `paintGray` renders the Bw plane **twice**, once
  for the base frame and again for the cleanup rebase, because a third
  framebuffer does not fit. The driver's own `frameBuffer` still holds the base
  frame after `setFramebuffer`, so `cleanupGrayscaleBuffers(display.getFrameBuffer())`
  may remove a whole render pass — verify the gray path does not clobber it first.
  **Do not confuse that with skipping the rebase.** Writing the gray planes
  leaves `Uc8279Driver::_oldPlaneValid` false ("gray planes overwrote
  DTM1/DTM2"), and `displayGrayscaleBase` treats that as `cleanBaseNeeded`, which
  takes the full B/W path — a 693 ms black flash. The rebase is what makes the
  *next* paint differential. Drop it and every paint flashes.

**Why the panel flashes black on the first two paints after a boot**

Not random, and not ours: `Uc8279Driver` sets `_initialFullsRemaining = 2` at
init, and `displayGrayscaleBase` forces the clean B/W path while that budget is
unspent, so the first content screen after boot is a true clear rather than a
differential against whatever the panel held. Exactly two paints, every boot.
The `display.requestResync()` in `setup()` sets `_forceFullSyncNext` as well,
which is **redundant** with that budget — it changes the count from two to two.

The corollary is a real gap 2B left: `RefreshPolicy`'s FULL-every-15 is computed
and logged but **never reaches the panel for a grayscale screen**, because
`paintGray` hardcodes `HALF_REFRESH` as the fallback and the driver decides for
itself. So no periodic full clear is scheduled on chrome screens at all. Whether
that matters is empirical — differential grayscale may not ghost badly enough to
notice. Watch for the panel looking dirty after heavy navigation; if it does, the
fix is to route the policy's decision into `displayGrayscaleBase`'s fallback and
force `_forceFullSyncNext` on a cadence hit.

That gap **closed itself** when chrome left the grayscale path: the one-pass
paints (`paintMono`, `paintDithered`) pass the policy's decision straight through
as `FULL_REFRESH`/`FAST_REFRESH`, so FULL-every-15 now reaches the panel on every
screen. It reopens only for a screen that declares `Grayscale`.

## Matching the reference firmware's chrome (2026-08-21)

The stock firmware is **CrossInk**, a CrossPoint derivative. Reading its source
settled three things we had guessed at, and the user then compared the two
firmwares on the same X3 and preferred CrossInk's chrome. All of the below is
verified in its code, not inferred from its behaviour:

- **Its chrome has no anti-aliasing at all.** UI fonts are built **1-bit**; only
  the reader fonts are 2-bit. Its "Text Anti-Aliasing" setting is referenced
  *only* in the EPUB and TXT reader activities — never in a menu, home, library or
  settings screen. So the setting is a book-text setting that happens to be
  spelled generically.
- **Its refreshes are FAST by default.** `GfxRenderer::displayBuffer()` defaults
  to `FAST_REFRESH`, and every list and menu screen calls it with no argument.
- **It does not full-refresh chrome on the X3.**
  `ScreenTransitionRefresh::modeFor` returns FULL only for
  `screenChanged && !gpio.deviceIsX3()`. Home's single `FULL_REFRESH` sits behind
  an `initialFullRefresh` flag that defaults to false. There is **no windowed
  refresh** (it is commented out) and **no periodic full-refresh cadence** anywhere
  in its UI.

What changed here as a result: `Fidelity` gained a third option and `Mono` became
the default and what chrome ships; `RefreshPolicy` gained `fullOnTransition`.

**Where that landed, after the cadence was tried both ways** — and this
supersedes an earlier draft of this paragraph, which said the shell passes
`fullOnTransition` false and keeps a FULL-every-15: it is the other way round.
The shell takes **`fullOnTransition` true and NO periodic cadence**
(`kNever`). A flash on a *screen change* is expected on an e-reader, as Kindle
and Kobo do it, because a differential update there has a whole screen of stale
content to ghost through; a flash on a *focus move* is a defect. The 1-in-15
cadence put the flash on an arbitrary navigation instead, which read as more
random than the transition flash it replaced. Nothing has ghosted without it, and
the ink accumulation this project did once see came from a missing grayscale
settle pass on a path chrome no longer takes. Both are `reader::Settings` fields
as of 2C-1; the reasoning lives above the declarations in `shell/src/main.cpp` so
that "CrossInk does not do this" cannot flip either one without someone deciding
to accept the trade.

And what it says about 2A-2: that phase measured 1-bit thresholded chrome as
illegible, and the real variable was the **px-authored type ramp**, not the
threshold. The pt-at-150-DPI ramp put every role at ≥ 21px, and at 21px a fully
inked 2px stem is *more* legible than the same stem stippled at 5/8 density — the
stipple reads as noise on the stroke, not as a soft edge. The one element on Home
that measurably got worse is the 67px `6%` numeral, whose curves went from smooth
to a countable staircase; that is precisely why `Dithered` is kept as a real,
reachable option rather than deleted.

**2C — The screens**
Library browsing real files over SD, the settings store and screen, Sleep,
SD-missing, and Home's empty and missing-book variants. Split into three plans,
because it is more than one plan's worth and it divides cleanly:

- **2C-2 — Library over real files, item actions, delete confirm, book details.
  DONE.** Six of V1's 28 designed screens now render and match at both
  geometries. What it settled beyond its own scope, and what it left:
  - **Overlays render the stack**, and the shell must call `App::render`. Calling
    `top().render` paints a panel on white and **no desktop test can see it** —
    the sim and every golden go through `App::render`. That bug was written and
    caught; `shell/` having no harness is the standing hazard behind it.
  - **The session stores a screen NAME.** Inserting screens into `ScreenId`
    silently repointed stored ordinals.
  - **`/books` is created if absent**, because an empty Library and an unreadable
    card are the same screen otherwise. A failed create is logged, not fatal, and
    Home's row then shows no count rather than a 0.
  - **Left approximate, knowingly:** the record holds one screen id and no
    **path**, so sleeping in `/books/Classics` on row 3 wakes on `/books` row 3 —
    a plausible-looking wrong row. And sleeping with an **overlay** up stores the
    overlay, which the wake cannot rebuild, so it lands on Home and loses the row;
    storing the topmost non-overlay needs an `App` accessor below `top()`.
  - **`countLibrary` costs one directory listing per folder at boot**, before the
    first paint. Fine on the dev card, unbounded on a card with fifty folders.
    Phase 3's background library scan is where it belongs.
  - **The comparison tool re-centres absolutely-positioned panels** when
    re-rendering a board at the other geometry. Seven boards needed it, five of
    them Phase 3's and 4's — so the X3 design column had been wrong for every
    overlay in the project, which is the worst way for that tool to be wrong.
  - **Two overflow gaps left, both found while fixing titles.**
    `drawDetailRow`'s **value** is not width-limited, and Book details has a
    `Location` field holding a path — a deeply nested folder runs the value into
    its label, on the very screen the title work was about. `drawRow`'s and
    `drawPanelRow`'s labels are literals today so cannot overflow, but
    `renderStub`'s are not (2C-3 deletes it). No board declares truncation for
    any of them, so each needs a board pass first.
  - **`elideToWidth` cuts between codepoints, not grapheme clusters.** Nothing in
    the typographic set or Latin-1 is multi-codepoint, so nothing today hits it —
    but real EPUB metadata (Devanagari, Arabic, family emoji) will separate a
    combining mark from its base. Same shape as `upperAscii`'s documented
    ASCII-only limit; a cluster boundary needs a table `core/` does not carry.
  - **The delete confirmation wraps rather than eliding**, against the letter of
    "ellipsis everywhere but book details". Its caption is a sentence with a name
    in it, and every truncation loses the closing quote and the question mark — a
    confirmation that stops reading as a question is one people dismiss unread.
    Flagged to the user and left wrapped.
  - **Overlay repaints are cheap now**: `veilRect` is 13.6x faster byte-wise
    (2.33 -> 0.17 ms full-frame) and a focus move inside an overlay repaints the
    overlay alone (4.75 -> 1.58 ms). The partial path is gated on
    `Screen::paintFootprint()`, because an overlay panel is 1px taller when its
    last row is focused and a naive partial repaint left a stale hairline.
    **Grayscale is excluded** and refuses rather than half-working.
- **2C-1 — storage, settings, SD-missing, wake restore. DONE**
  (`docs/superpowers/plans/2026-08-21-phase2c1-storage-foundation.md`). `core/`
  has a `FileSystem` interface with three implementations held to one contract, a
  minimal flat-JSON reader, a settings store at `/.reader/settings.json`, the
  SD-missing screen with a retry that really re-mounts, and an NVS session record
  that survives a wake with no card in the slot. See **Storage** in `CLAUDE.md`.
- **2C-2 — Library over real files**, item actions, delete confirm, book details.
- **2C-3 — Settings, Sleep, Home's empty state. DONE**
  (plan: `2026-08-22-phase2c3-settings-sleep-states.md`). **V1's chrome is
  complete**: nine boards implemented, `StubScreen` and `InputMonitorScreen`
  deleted, and flash fell 2,430 bytes on the deletion — the check that a removal
  really removed something.
  - **Settings draws nine rows and three respond**, with focus skipping the rest.
    See CLAUDE.md; the decision was between that and shipping a screen with
    controls that do nothing.
  - **Wi-Fi was cut from V1** mid-phase, which took nine boards out of the sheet
    and brought Settings' list back inside the panel. The rail it had grown came
    straight back off, and nothing but the board and the item table changed —
    `renderSettings` asks `totalRows > rows` rather than assuming, so Phase 3's
    typography settings will make it scroll again on their own.
  - **`HomeMissing.dc.html` was found not to be a state.** Structurally identical
    to Home — same CONTINUE block, same hints — differing only in demo data and a
    menu style Home had moved on from. Either it was never finished or it is a
    duplicate; **what a missing-book Home looks like is still undesigned**, and
    that is the one thing 2C-3 did not deliver.
  - **Every screen was measured, not eyeballed**: 1.85%–2.35% design-vs-firmware
    mismatch with rule positions identical at both geometries. Three rules the
    Settings board draws and a naive renderer does not were found that way, and one
    of them was shifting every row below it by a pixel. `make compare` reports
    "firmware ok" for rendering successfully, **not** for matching — the mismatch
    count is a separate question, and asking it is what found all three.

**A DEFECT THE FOCUS REWORK AND HELD-SCROLL CREATE TOGETHER, and neither owns it.**
Wrapping is on (`Focus::move()` wraps by design) and a held Up or Down delivers a
*distance* (`InputEvent::steps`), so **holding Down on the Library now cycles for as
long as the button is down instead of resting at the end**. Both halves are correct
alone: a wrap can never read as a dead button, and a time-derived distance is the
only thing that scrolls usefully on a panel that blocks its own loop. Together they
mean a long hold has no end.

**FIXED**, and the fix needed an abstraction first. `Focus::move(delta, held)`
clamps when the flag is set — a wrap belongs to a press, a hold rests at the end —
but nothing on the path knew a movement had come from holding, which is precisely
why the defect belonged to neither half that created it. So screens now answer
`GestureEvent`s (`gesture.h`) rather than raw presses, and `held` rides on the
gesture. `LibraryScreen` forwards it and has no opinion.

That refactor paid for itself twice over: six screens had been opening with
`if (ev.kind != PressKind::Short) return none();`, a guard whose omission silently
lets a hold do a press's job, and nine had overridden `longPressable()` with the
same expression — the same fact the hint bar already states, in two spellings.

**What 2C-2 and 2C-3 inherit from 2C-1, and what to watch:**

- **The stored focus was 0 in 2C-1, and 2C-2 made it real** — the two virtuals
  it predicted (`Screen::focus()` / `setFocus()`) landed with Library, exactly as
  planned, and the shell now stores the live focus and restores it on wake.
  Recorded as DONE rather than trimmed, because the prediction being right is the
  useful part. (Both this and CLAUDE.md still asserted "always 0" afterwards; a
  cold-read review caught it. **An inherited-work note is a claim with an expiry
  date — close it in the phase that consumes it.**)
- **A restored session is one screen deep**, pushed onto Home. A record naming a
  screen that was two deep (Settings > Input Monitor) comes back with Home
  underneath it. Nothing in V1 is unreachable that way; a restored *path* is
  2C-2's call if the deeper screens make it worth one.
- **`FileSystem` has no streaming, and that is Phase 3's gap, not a bug.**
  `readAll` is for the small JSON files V1 stores — `SdFileSystem` caps it at
  64 KB. EPUBs are megabytes against ~230 KB of heap, so **`readAll` is not the
  EPUB path**: Phase 3 adds a handle with `read(buf, n)`, which is a different
  shape, and designing it with no consumer would have meant guessing.
- **The path normaliser exists in three copies** — one per implementation, in
  three build worlds — and the only thing holding them together is the contract's
  "a redundant or trailing separator addresses the same thing" clause, run against
  all three. A fourth implementation should extract it.
- **A card pulled after a successful mount needs a reboot.**
  `SDCardManager::begin()` short-circuits on its own `initialized` flag and the SPI
  path has no `end()`/`unmount()`, so it reports success without touching the
  hardware. The shell therefore requires a `probe()` (a real root-directory read)
  to agree before it accepts a mount, and says so in the log when it cannot.
  Retry works for the case the screen exists for — no card at boot. **2C-2's
  Library must expect `mounted()` to go false under it**, mid-session, with no way
  to recover except a reboot.

Inherited from 2B, which deferred these deliberately:
- **The Sleep screen.** 2B sleeps without painting, which looks correct because
  e-ink holds its last image — the device keeps showing what you were reading.
  `design/Sleep.dc.html` exists; wire it into `sleepNow()`. **2C-3.**
- **Restoring the last screen across a wake. DONE in 2C-1** — over NVS rather
  than the settings file, because a wake must work with no card in the slot.
- **Replacing the provisional stub surface.** `StubScreen`, `StubViewModel` and
  `Theme::renderStub` are scaffolding carrying a visible `PHASE 2C` note, so that
  no invented visual could be mistaken for design. Build Library and Settings
  from their boards and delete what is left. `InputMonitorScreen` can stay as a
  diagnostic or go with it.
- **Making the refresh and power knobs real settings. The STORE is done in
  2C-1**; the screen is 2C-3's. The three named constants in `shell/src/main.cpp`
  — `kSleepAfterMs`, `kFullRefreshEvery`, `kFullOnTransition` — are now fields of
  `reader::Settings`, and the struct's defaults are the values that were compiled
  in, so a device with no file behaves exactly as before. Settings already designs
  rows for the first two.
  - `kFullOnTransition` is the one that needs a **new** row, so the board gets it
    first (design-first rule). V1 hardcodes it true — a screen change takes the
    FULL/GC waveform so the outgoing screen cannot ghost through, matching Kindle
    and Kobo and deliberately diverging from the reference firmware, whose
    settings screen ghosts visibly on this device. It costs ~825 ms against
    ~520 ms, so wanting it off for quicker navigation is a legitimate preference
    rather than a workaround. See spec §10.
- **Home's hint labels do not follow focus.** Home's board says
  `READ / SELECT / UP / DOWN` and 2B renders exactly that. If Confirm should read
  `OPEN` over the Library row, that is a board edit first.

**Exit:** `make compare` shows every V1 screen implemented and matching.

### Boot and resume — measured 2026-08-22

Not a phase; findings that outlive the work that produced them.

**Boot to first paint went ~4000 ms → 1810 ms**, and what remains is attributed:

| | ms | |
|---|---|---|
| USB CDC wait | 0 | was an unconditional `delay(2500)` |
| Panel detect | 132 | |
| `display.begin()` | 81 | |
| Fonts | 42 | |
| Body face | 9 | was 371; the 95-glyph sweep is now opt-in |
| SD mount | 20 | |
| **Settings + `countLibrary`** | **610** | a `/books` listing at ~2.7 ms/entry |
| Render | 76 | |
| **Panel waveform** | **808** | PON 40 + DRF 693. Physics. |

Three lessons, all of which cost something:

- **A `delay(2500)` was hiding in plain sight** and was blamed on `XteinkDetect`
  for two commits, because the only timestamps in a boot log came from the SDK and
  the first of those was read as time zero. `mark()` now leads with `millis()`.
  **A log's first timestamp is not time zero.**
- **Two of the boot's costs were diagnostics I had added** — the `[library]` probe
  (2 listings, ~2.1 s) and the `[body]` sweep (~362 ms) — both left unconditional
  after the measurement they existed for was taken. Both are now behind flags.
  A diagnostic that costs seconds of boot quietly becomes the product's behaviour.
- **What's left is one listing and one waveform.** The waveform is the panel. The
  listing is on the critical path only so Home can show a count, and persisting
  that count is the same work as the sorted index that lifts the library cap.

**A RESUME ON BATTERY IS A POWER-ON RESET.** With USB attached the chip really
deep-sleeps and returns `ESP_RST_DEEPSLEEP`; on battery the same sleep leaves it
fully powered down, so pressing power gives `ESP_RST_POWERON` — indistinguishable
from a first-ever boot. The restore was gated on "did we wake", so on battery it
declined every time and cleared a good record: the symptom was "it always comes
back to Home", and the code was right about a question that had no answer. The
intent is now recorded (`markSleeping()` / `takeSleptFlag()`, one flag buys one
resume) rather than inferred. **Verified on device.**

**A WAKE IS NOT OBSERVABLE THE OBVIOUS WAY**, and this cost four captures:

- Deep sleep powers down USB, so a resume must re-enumerate — and on the C3 a host
  attaching can reset the chip (`ESP_RST_USB`). Three attempts to log a resume came
  back as cold boots. A session restore that "stops working" while a logger is
  attached is the restore correctly declining.
- `serial-log.py --wait-for-port` polls for the port, and its retry must clear
  DTR/RTS before opening — the first version reset the device it was waiting for.
- **Facts have to be kept in NVS, not `RTC_DATA_ATTR`.** ESP-IDF re-initialises
  `.rtc.data` on every reset that is not a deep-sleep wake, so plugging in to read
  the record erases it — and the log comes back with no `[prev]` line, which reads
  like broken instrumentation rather than wrong storage. `encre_diag` holds it now.

### Phase 3 — Reader engine

**The engine is OURS.** `freeink-sdk/libs/book/FreeInkBook` — a complete MIT EPUB
engine in the submodule we already ship — was evaluated and rejected on control of
the reading surface. Spec §3.1b carries the decision, the measurements and the
five findings that applied either way. Do not re-litigate it without reading that.

**3A — Foundations. DONE** (plan: `2026-08-21-phase3a-reader-foundations.md`)

Reclaimed the memory the reader needs, stopped paying for a framebuffer twice,
taught the filesystem to stream, and gave body text a face that can be any size.

- **+152,792 bytes of heap, device-confirmed** (`heap=223892`, was `71100`):
  99,008 from replacing two `unordered_map`s per face with a binary search over
  the blob's already-sorted records, and 52,272 from rendering into the driver's
  own framebuffer instead of memcpying into it. Both pixel-neutral.
- **A seekable read handle** (`openRead`), because a zip's central directory is at
  the end of the file and a forward-only stream cannot read an EPUB at all. Ten
  contract clauses, run against the fake, the host **and the real card**.
- **Body text rasterises at runtime** from `stb_truetype`; chrome keeps the
  pre-rendered ramp. One text path through `GlyphSource`, which cost nothing —
  Home renders 2.5% FASTER, because separating `advance()` from `glyph()` means
  measuring reads one number instead of decoding a whole `Glyph`.
- `tools/ttfprep.py` strips what stb cannot read: **955,132 → 132,724 bytes**, all
  1,789 glyphs intact, proven pixel-for-pixel against the original.
- **Kerning, which this project had never had.** Both faces keep it in GPOS where
  neither `fontc.py` (legacy `kern` only) nor stb (LookupType 2 only) could see
  it, so all twelve assets had zero pairs. Synthesising a legacy table cut
  **design-vs-firmware mismatch by 27.6%** (221,813 → 160,688 px) and made
  DeleteConfirm's paragraph wrap to the board's own four lines instead of five —
  the divergence flagged in 2C-2 and never resolved.

**The rasteriser, measured on the part** (`[body]` at boot, X3/UC8279, ppem 29).
3B rests on these three numbers, so they are here rather than in a commit message:

| | Measured | What it means |
|---|---|---|
| Cold raster | **3,794 us/glyph**, 360 ms for 95 | The first page of a chapter. Fine — the panel's own full refresh is 808 ms. |
| Warm raster | **6 us/glyph**, 571 us for 95 | Every page after. **631x.** The cache is the difference between viable and not. |
| Measure | **17.3 us/char** (1,213 px in 1,507 us) | Never rasterises (`rast=0`, checked on device). But see below. |

The one-sample figure this replaced was **7,845 us** — the first rasterisation in
the process, paying for first faults into 132 KB of font in flash, stb's first
scratch malloc and a cold icache. Planning against it would have put the reader's
budget 2x off on a cost that never recurs. **One sample cannot tell a cold path
from a steady one; do not accept one for a number a phase depends on.**

**The 72 KB boot dip was this probe, not bring-up** — and finding that out is
what the heap trace on `mark()` is for. `min` is flat at 229,900 through
`display-begin-returned`, `fonts-ok` and every later stage, and falls to 155,712
at exactly `body-face-ok`. The correction matters in both directions: there is no
mystery allocation in bring-up, and the spike is not a boot cost that happens once
— it is what rasterising a glyph costs, so it recurs on every page the reader lays
out.

**Where it goes is one line of stb.** `third_party/stb_truetype.h:2802` sizes the
active-edge heap as `count = (size < 32 ? 2000 : size < 128 ? 800 : 100)`. The v2
`stbtt__active_edge` is 28 bytes (a `next` plus six floats), so `size < 32` and the
first edge of **every** glyph triggers a single **56,004-byte** malloc for 2000
slots, where body text needs perhaps twenty. `stbtt__hheap_alloc` chains a further
chunk when one runs out, so the count is purely a memory-against-allocation-count
trade with no correctness dimension: `64` would make it 1,796 bytes.

It is deliberately NOT patched. The file's header makes a verifiable
"vendored, unmodified" claim with a sha256, that claim is worth more than 54 KB
while 54 KB is affordable, and a local edit is a thing to re-apply on every
upstream bump. So this is recorded as a lever rather than taken: **if 3B's budget
gets tight, that one line is 54 KB of headroom**, and the way to confirm it worked
is `min` on the stage trail, not reasoning. What must not happen is 3B discovering
a 56 KB floor by allocating into it — the reader's own cache, zip directory and
page structures all land on top of this spike, and it is invisible to every
`getFreeHeap()` in the firmware.

Two hard constraints fall out, both new:

- **THE 8 KB GLYPH CACHE DOES NOT SCALE, and the default is already at its
  limit.** Printable ASCII at ppem 29 is `7785/8192 bytes, 95/128 entries,
  evict=0` — a 5% margin, and that is before a single accent, em dash or curly
  quote, all of which the fixtures contain. Glyph bytes go as ppem^2 (2bpp,
  `ceil(w/4)*h`), and book CSS asks for **16, 32, 41, 51 and 64 px**: at 64 px the
  same 95 glyphs need ~38 KB, and a realistic ~120-glyph set ~48 KB. Under the
  default the arena would thrash, and thrashing does not cost a little more — it
  costs the 631x, turning a 571 us page into seconds. **3B must size the budget
  from ppem and the page's distinct-glyph count, not take the default**, and the
  eviction counter is how that is checked rather than argued. Heap allows it
  (48 KB against 223 KB free); the accounting to remember is that the budget buys
  the ARENA and the entry table is charged on top — 8 KB of budget is 11,776 bytes
  of heap, 44% overhead.
- **WHOLE-BOOK PAGINATION IS NOT VIABLE.** Measuring is cheap per call and there
  are a great many calls: 17.3 us/char over a ~1.8M-character novel is **~31
  seconds**, once, before the first page draws. Per-chapter or lazy pagination with
  a persisted page map is therefore a requirement, not an optimisation. The per-char
  cost is itself reducible — each char pays a cmap binary search plus two more for
  the kern pair lookup, and a 256-entry direct-mapped advance/gid cache for Latin-1
  would be a few hundred bytes against most of that 17.3 us.

**WIRING THE SLEEP SCREEN IS PHASE 3'S, and it is the one piece of 2C-3 that
shipped without reaching the panel.** Board, screen, theme method, simulator
subcommand and tests all exist; the shell's sleep path never renders it, so the
device keeps whatever screen the user was on.

Deferred on purpose. The board's content is a reading card --
`NOW READING / MIDDLEMARCH / 6% · CH. 01` -- and until there is a Reader the device
would paint demo fiction or an empty block. Wiring it needs a real current book,
which is exactly what 3B and 3C produce.

Two things to know before doing it:

- **Paint it WITHOUT pushing it.** The session record names the top screen, so a
  pushed `SleepScreen` makes the wake restore into the sleep screen. It wants a
  direct render after the record is saved.
- It costs a **full refresh (~825 ms) on every sleep**, on top of the ~808 ms the
  first paint after a wake already costs.

**What 3B and 3C inherit:**

- **Kern records are whole pixels and the error compounds.** `CH. 01 — MISS
  BROOKE` has three ~−0.6px pairs that each round to −1: −3px against Chrome's
  −1.906. The fix is 1/64px records, which needs an `.rfnt` v3 and a
  `Font::kerning` unit change — and would halve the 225 KB the tables cost.
- **`advance()` returns whole pixels.** Correct for the pre-rendered ramp (integral
  by construction), wrong for a scalable face: up to 0.5px lost per glyph with no
  fraction left to recover, which is the accumulation `Tracking` exists to
  prevent. Widening re-blesses every golden, so it wants to be a deliberate task.
- **`stb_truetype` range-checks nothing on untrusted input** — its own header says
  an attacker can read arbitrary memory. `looksLikeSfnt()` covers a truncated
  asset; it does **not** cover a font arriving off the card via `@font-face`,
  which EPUBs can do. Embedded fonts need a real validator or an allow-list.
  Such a font would also get no kerning, since nothing synthesises for it.
- **SdFat has ONE 512-byte sector cache** on this part. Two handles interleaved in
  the same file are correct but every alternating read is a real card read; a zip
  reader ping-ponging between the central directory and an entry will be
  pathologically slow. Read the directory into RAM once.
- **`readAll`'s 64 KB cap is `SdFileSystem`-only.** The host and fake have none, so
  a 3B path using `readAll` on a 200 KB file passes every desktop test and fails on
  device. Use `openRead`.
- **The handle has no `error()`.** A short read below `size()` plus `mounted()` is
  the whole signal. If 3B must tell "truncated EPUB" from "card pulled mid-book"
  to show different screens, that is a new method and a new clause.
- **`lendBuildStorage()` now has a real relationship with the frame.** While it is
  lent, paints are skipped and logged, and the paint after the return is forced
  FULL because the return wipes the frame white. 3C must return it before anything
  wants a screen — **including the SD-missing screen a card pull would push**,
  since the presence poll runs from the same loop.
- The em dash renders as a comb on the dithered path at body size — a thin
  horizontal stroke against the 4x4 grid, the same failure class CLAUDE.md already
  records for `kChevron`'s diagonal. First thing to fix if the Reader ships
  `Dithered`.

**3B — A thin end-to-end slice. DONE** (plan: `2026-08-22-phase3b-reader-slice.md`)

A file on the card to a justified page on glass, through six layers each ignorant of
the next. **Nothing was vendored** — miniz and expat are named below the line for
reasons that did not survive measurement: an EPUB is well-formed XML by
specification, so none of the tag-soup recovery that makes an HTML parser large is
needed, and `stb_image`'s zlib was already in the build for PNG.

| Layer | Bytes | Refuses |
|---|---|---|
| `inflate.h` | 3,001 | anything not filling the pre-sized buffer exactly |
| `zip.h` | 3,402 | encryption, unimplemented methods, >512 entries, >512 KB entries |
| `xml.h` | 4,215 | bad entities, names >128 bytes, >16 attributes |
| `epub.h` | 6,306 | no container, no rootfile, unparseable OPF, empty spine |
| `document.h` | — | unbalanced tags, nesting >64, >4,096 blocks |
| `layout.h` | — | nothing; it measures |

Plus `book.h`, the seam to the filesystem, in `core/` rather than `shell/` **because
`shell/` has no test harness and five bugs have hidden there**. 638 test cases.

**Measured, and three of the plan's own premises did not survive it:**

- **0 rasterisations across 6,800 pages of layout.** Design decision 3 of 3A, on
  real data rather than on the discipline of not calling `glyph()`.
- **The glyph cache had to grow, but not for the stated reason.** The plan sized it
  from "printable ASCII fills 7,785 of 8,192 bytes at ppem 29 with no margin". A
  PAGE is far smaller than ASCII — the worst of 5,000 real pages used 36 distinct
  glyphs and 3,272 bytes, and 8 KB evicted nothing. What matters is the UNION across
  pages, because the arena is a ring: at ppem 32 that is 12,292 bytes, so 8 KB held
  the set at **no** reading size. Now 16 KB, with the ppem table in
  `scalablefont.h`.
- **Justification's refusal rule was measuring the wrong thing.** A per-gap stretch
  cap cannot tell a corridor from prose. On `Reader.dc.html`'s own copy it refused
  an 83%-full line by one pixel and set it ragged under a line it had justified.
  Replaced by a test on how full the LINE is: ragged lines 18% → 3.4%, justified
  71% → 86%.
- **A paginator is not `overflow: hidden`.** The X4 board clips a 13th line
  mid-glyph; the firmware omits it, which is what a reader must do. That is a
  permanent, correct difference in the comparison sheet.

**Against the board**, measured rather than reported as "ok": every line's top
within **1px** at both geometries, header and footer included. On the X4, 97% of the
residual ink difference lies within 2px of ink in BOTH images and no 1px shift
improves it — antialiasing, not placement — and every line break agrees with
Chrome's. On the X3 one line breaks a word earlier and resynchronises three lines
later: a sub-pixel measurement landing on the wrong side of one break decision, the
same class as `SdMissing`'s `max-width` note.

**Reader is the first `Fidelity::Grayscale` screen**, so its golden is the first that
is not a 1-bit frame — and `golden::checkGoldenGray`, unused since the grayscale path
landed, has its first caller.

**Desktop costs** (12-line page, 444px column, ppem 32): paginate 349 µs/page, lay
out one page 168 µs, draw 580 µs cold / 363 µs warm. The device rasterises at
~3,794 µs a glyph, so a cold page is ~110–140 ms there; the `[open]` serial line
reports parse, total, blocks, pages and the heap cost of an open.

Two fixes fell out of the work rather than the plan: `screenName` had been logging
`"?"` for `ScreenId::Sleep`, and Sleep's progress bar painted its fill **over** its
own border where all three boards declare `box-sizing: border-box` — which survived
because **Sleep had no golden**. It has two now, and the bar is one primitive.

**What 3C inherits from 3B:**

- **Page numbers are CHAPTER-RELATIVE.** The footer reads `1 / 2` where the board
  reads `53 / 890`. A book-wide number needs an index of every chapter's page count,
  which is a pass over the whole EPUB — and 3A already measured why it cannot be
  eager: 17.3 µs/char over a 1.8M-character novel is ~31 seconds. `ReaderViewModel`
  carries the two numbers plainly so that pass can fill them in.
- **A book is REOPENED per chapter.** `openChapter` reads one chapter and closes the
  file, because the alternative is a card handle held across a sleep and across a
  card removal. That costs a central-directory parse per chapter turn, not per page.
- **Home's CONTINUE still answers `none()`**, and `Reader` is nameable in the session
  record but the factory refuses to build one: a reading position is a block and a
  line, which the record's `focus` int cannot carry, so a restored Reader would
  reopen at page 1 and lose exactly what the record exists to keep. **Progress
  persistence is the prerequisite for both.**
- **`Activate` in the Reader is a known no-op** — it opens `ReaderMenu.dc.html`,
  which is not built.
- **Heading, blockquote and list-item styling is UNDESIGNED.** `document.h` carries
  the kinds and layout gives them all one line box; `Reader.dc.html` shows a
  mid-chapter page of paragraphs only, and the chapter title has nowhere to go —
  the header band carries `CH. 01`, not the title. **That is a board task before it
  is a code task.**
- **No hyphenation, and the justification threshold is untuned against real prose.**
  A line at the 60% threshold has 40% of its column as slack. The trade was made
  toward wide gaps because a ragged line mid-paragraph reads as the feature being
  broken; a hyphenation dictionary would let the threshold tighten.
- **No widow or orphan control.** The rules trade blank space at the foot of a page
  for a tidier break, and on a 12-line page that trade is expensive enough to want
  measuring before it is made.

**3C — A reader whose memory does not depend on the book. DONE**
(spec: `2026-08-22-phase3c-bounded-reader-design.md`)

3B read one chapter at a time, which was the right unit and was not enough: a
chapter is not a bounded quantity. Measured on `Le Fléau` (12.7 MB, 92 chapters,
mean 75 KB of XHTML): the longest chapter needed a **546 KB peak** against ~142 KB
free, and **62 of 92 chapters could be opened**. Per-book cost was never the problem
— the zip directory plus the OPF is 10,216 bytes.

Every layer became a stream. Measured over the same book afterwards:

| | 3B | 3C |
|---|---|---|
| peak for any chapter | 546,000 B | **69,884 B** |
| largest single allocation | ~316,000 B | **36,956 B** |
| chapters openable | 62 / 92 | **92 / 92** |

The whole book is 8,137 pages. Desktop timings: worst index pass 41.6 ms, worst
forward page turn **1.16 ms**, worst backward turn 33.9 ms.

**The decoder is ours** — `reader/inflate_stream.h`, raw DEFLATE in bounded chunks.
Not a preference: stb's is one-shot and there is no way to get chunks from it, so
every route to bounded memory needed a streaming decoder. It also removes stb's
6,608-byte single stack frame, which had already panicked the device. Validated
byte-for-byte against the shipping one-shot decoder: 216 entry-passes over the real
book at two grain sizes, 3,600 over the 200 generated EPUBs, zero disagreements.

**Three measurements corrected an assumption each:**

- Sizing the tokenizer's buffers. Over the book's 143,119 attributes the longest
  value is 49 bytes and the fattest tag carries 160; text runs are median 46, longest
  812. So `kTextBytes` is a chunking granularity, **not a limit** — a longer run is
  several `Text` nodes, which every caller already handles.
- Putting the arrays in one heap block. With the window on the heap but the tables as
  members, an `Inflater` local cost 6,336 bytes of stack — barely better than what it
  replaced. One `Scratch` brings it to 3,072.
- A `PageBuilder` needs no block window, because a `LaidLine` owns its text. That one
  decision removed a whole subsystem from the design.

**What 3D or later inherits:**

- **Page numbers are still chapter-relative.** The footer reads `3 / 12`. Book-wide
  needs an index of every chapter's page count — 92 decodes for this book — which is
  now affordable in memory but not in time at open. It wants persisting.
- **The index pass is the open cost.** One decode of the chapter before the first
  page draws: 41.6 ms desktop, so a few hundred ms on device for a long chapter. A
  persisted page map would remove it.
- **A backward turn re-decodes.** Fine at 33.9 ms desktop; worth measuring on glass.
- **`Activate` NO LONGER a no-op**: the reader menu and the chapter list are built
  (`screen_reader_menu.{h,cpp}`, `screen_contents.{h,cpp}`, `toc.{h,cpp}`). Home's
  CONTINUE still answers `none()`, and a `Reader` is still nameable in the session
  record but unbuildable by the factory — all three wait on progress persistence.
- **Heading, blockquote and list-item styling is still undesigned**, and the chapter
  title still has nowhere to go. A board task before a code task.
- **`Reader.dc.html` SHOWS A HALF-LINE, which the firmware cannot render.** Its last
  body line is sliced in half lengthwise (`dressed alike which is`), because the text
  block is `flex-grow: 1; overflow: hidden` over a column whose height is not a whole
  multiple of the 54.4px line box. `PageBuilder` lays out WHOLE lines only, so the
  board shows something the implementation cannot, and overstates how much text a page
  holds — while `make compare` reports the screen as `firmware ok`. Found while
  boarding 3D. `ReaderAnchored.dc.html` mirrors the column deliberately, so fixing
  `Reader.dc.html` fixes both; `Peek.dc.html` does not have it, because its panel is
  sized by its text.

**3C and beyond** (the original scope line, kept for what is left of it — the
container and the parse are done and were not vendored):
TXT importer; layout engine refinements (hyphenation, widows and orphans);
pagination + SD cache keyed by settings hash; Reader screen, reader menu,
typography panel (live re-paginate), contents, go-to-page, bookmarks, book
details, progress persistence, corrupt-book dialog.
**Exit:** read a real EPUB end-to-end on device; golden layout tests with
known page breaks.

**Read CrossInk's reader path before designing ours.** Chrome now matches the
reference firmware (see "Matching the reference firmware's chrome"); body text is
the half of that firmware we have *not* mined, and it is the half where it spends
its 2-bit fonts and its anti-aliasing setting. Three specific things to look at:

- **`--darken-aa` coverage thresholds.** Its reader font build darkens
  anti-aliased coverage on a different ramp than `fontc.py` uses — **3/6/10 against
  our 4/8/12**. Lower thresholds mean more coverage lands on a darker level, which
  on this glass is the difference between body text that reads solid and body text
  that reads grey. Worth rebuilding Literata both ways and comparing on the panel,
  not on a monitor.
- **Strip grayscale.** The device log reports `strip=1`, so the driver supports it.
  We rejected it for *chrome* because rotation is CCW and a row band becomes a
  full-height column band — but a **page turn** repaints the whole text column, so
  the geometry that killed it for a focus move does not apply the same way. Re-ask
  the question here rather than inheriting the "rejected" verdict.
- **Async overlap.** CrossInk overlaps rendering with the panel's BUSY wait. Its
  SDK's own migration doc measures **1274 ms → 822 ms** from that alone, which is
  larger than any single win left in our paint path. This is the one item here that
  would also benefit chrome.

**3D — Peek and return. DESIGNED AND BOARDED, NOT BUILT**
(spec: `docs/superpowers/specs/2026-08-24-peek-and-return-design.md`;
boards: `Peek.dc.html`, `ReaderAnchored.dc.html`)

**Going somewhere in a book and coming back.** Two mechanisms: a *return anchor*
recording where you were before you stopped reading linearly, and a *peek overlay*
showing a page of the book over the veiled page you are on.

It exists because of what needs it. `Contents` and `Bookmarks` are **useless without a
way back** — a jump that costs you your place is a jump readers learn not to make.

`GoToPage` was the third caller and is **cut** (2026-08-24): a reflowable book has no
stable page to go to, so the number a picker offers moves with the type size, and the
honest jump is the chapter name that `Contents` already gives. Its board and its
`ReaderMenu` row are gone. That leaves two callers rather than four, which weakens the
"primitive built first rather than extracted fifth" argument but does not overturn it —
`Contents` is built and the anchor is still what makes it safe.

- **The anchor is shippable alone.** Its caller is ordinary backward paging, so it
  needs no new screen — a footer field present only when there is somewhere to
  return to, and a bound `Up`. It rides the three existing save edges, so no new
  card write.
- **The anchor is a PAGE, not a chapter.** Page back three pages inside one chapter
  and `Up` returns to that page. It stores `(spine, block, line)` because a page
  *number* is chapter-relative and the high-water rule is entirely a comparison; the
  number the footer shows is computed by `openAtCursor`, not stored.
- **`Reader.dc.html` IS UNCHANGED, deliberately** — the no-anchor state is the common
  case and "the board unchanged" is the assertion worth a golden. The anchored state
  is its own board, `ReaderAnchored.dc.html`, the way Home's variants are.
- **The footer's progress bar YIELDS its slot to the anchor**, and that is arithmetic
  rather than taste: at 21px the bar plus both counters need ~482px against 444px of
  usable width. Nothing is lost — the bar is a graphical restatement of the
  percentage beside it, and both readings of progress survive. The mark is the `kUp`
  **icon**, not a glyph: U+2191 is outside `fontc.py`'s subset and would render as a
  notdef box.
- **The peek panel shows EIGHT lines, and the count is the design.** Content-sizing
  alone ran to eleven and filled the glass to within 48px of the top, which reads as
  a bordered full screen rather than a modal. Measured: 544px panel, 128px of veil
  above. A pinned height was worse still — it cut the last line in half lengthwise,
  which the firmware cannot even do, since `PageBuilder` lays out whole lines.
- **`Up` and `Down` are empty 36px slots in the peek, not PREV/NEXT.** `Up` already
  means "return to where I was" on the screen underneath, and one button with two
  meanings across a single press is worse than an unbound one — the side buttons page
  in the peek exactly as they do while reading. The four-label bar also left only
  ~4px of slack at 480 wide against faces that measure ~3% wider than Chrome.
- **`Contents` HAS LANDED, and it landed with no way back** — proof of this entry's
  premise rather than a prediction of it. `ContentsScreen` answers `Activate` with
  `Action::popTo(ScreenId::Reader)` and nothing records where the reader was, so the
  jump takes their place with it. The overlay's first caller therefore exists, and
  neither half of 3D is blocked any more.
- **A second `ReaderScreen` does not fit**, and the design turns on that: a live
  chapter peaks at 69,884 bytes with a 36,956-byte single allocation, against a
  45,840-byte floor. It works because the Reader beneath **releases** its chapter
  (all of `ChapterReader` is behind `unique_ptr`, and `pb_` is already nullable) and
  re-establishes it with one `seekTo` — 33.9 ms desktop for the worst page in a real
  book. One live chapter at any moment.
- **First overlay over a grayscale screen.** Every overlay today sits over the
  Library, which is `Mono`. `veilRect` per plane is unverified and gets a test.

**Exit:** page back twenty pages, press `Up`, land exactly where you left.

**3E — "Who's this character again?" DESIGNED AND BOARDED, NOT BUILT**
(spec: `docs/superpowers/specs/2026-08-24-names-design.md`;
boards: `Names.dc.html`, `NamesEmpty.dc.html`, a `Names` row on `ReaderMenu.dc.html`)

The question 3D was scoped out of. A reader meets a name 300 pages in and has no idea
whose it is. Kindle answers with X-Ray — precomputed on a server, reached through a
touchscreen. We have neither.

**THERE IS NO NAME DETAIL SCREEN, and that is the largest thing in the design.**
Selecting a row opens the **peek** at the introducing sentence, which deletes a
screen, its board, and the need to store any sentence text on the card — and makes 3D
the payoff rather than only a prerequisite. So 3E is three pieces: `ReaderMenu` (the
sheet is boarded, still unbuilt), a **name index**, and a **names list**.

**TWO MEASUREMENTS DETERMINE ALMOST ALL OF IT**, and both came from instrumenting the
probe rather than reasoning:

- **A whole-book candidate table is 85,001 bytes against the 45,840-byte heap floor**
  — 1.9× the entire margin before storing any sentence text — while the worst single
  chapter is 7,797. So the scan is **per chapter** and the accumulator is the card.
- **`filesystem.h` has no streaming write.** `writeAll` takes a whole buffer, so the
  persisted index must fit in RAM as one string. That independently rules out a
  stored sentence per name (~220 bytes an entry against ~20 for a cursor).
- **A run earns its slot** by being seen twice mid-sentence within one chapter, which
  takes the index to **17%** of the naive table: 738 runs / 14,812 bytes for
  `Le Fléau`, 167 / 3,300 for `Neuromancien`. Admission at the door, not eviction
  after — eviction by count thrashes exactly the mid-frequency names the feature
  serves.
- **The merge happens in the chapter-crossing window**, because that peak is ~37 KB
  and the window is the one moment the 36,956-byte inflate scratch is already free.

**The list is ALPHABETICAL, which inverts the obvious order.** The name you cannot
place is rare, so most-mentioned-first buries exactly what you came for and moves it
as you read on. You always arrive knowing the string. Navigation is the Library's rail
and auto-repeat unchanged; the rail earns more here, because with alphabetical
ordering a thumb halfway down means roughly "around M".

**Display threshold 5 mid-sentence mentions** — 300 groups on `Le Fléau`, 83 on
`Neuromancien`, 42 on Dexter. The tension is real: a higher threshold cuts precisely
the rare names the feature is for, a lower one is 89 screens.

**Two row heights, measured off the board: 90px with a fullest form, 60px without** —
a place or an already-full name has nothing for a second line, and that is 30–40% of
rows. Settings' problem and Settings' solution: the theme reports the box model, the
screen counts. **And the slack below the last row is an invariant** — a `ScrollWindow`
draws whole rows only, so slack varies, but 60px or more means another row would have
fitted.

The decisions the probe settled first, all still standing:

- **On device, as you read.** No desktop pre-processing, no network. It therefore
  only ever sees chapters already read, so it is **spoiler-proof by construction**
  rather than by a rule. And it rides a walk that already happens — the pagination
  pass decodes the whole chapter, so the scan is over text already in RAM.
- **The screen says `NAMES`, not `CHARACTERS`.** A capitalization-and-frequency
  heuristic cannot tell a person from a place, and separating them needs a
  per-language word list — a table `core/` has twice refused to carry. So a place in
  the list is correct rather than a defect. Same move as the footer's em dash.
- **The peek opens at the sentence that introduced the name**, chosen as the
  earliest of the best kind: prefer a name followed immediately by a comma whose next
  word is lowercase (the appositive is how novels introduce people, and the lowercase
  test kills the front-matter name-list case), penalise mostly-quoted dialogue. No
  language table. The plain first mention is often the useless one.
- **Reached from `ReaderMenu`**, whose row shows a **chevron, not a count**: Bookmarks
  counts something the reader made and can verify, where a names count is an artefact
  of the display threshold — 300 at five mentions, 713 at two.

**THE RISKIEST QUESTION IS ANSWERED: THE HEURISTIC WORKS.** `tools/name_probe.cpp`
(built by the `name_probe` target, not in ctest — it needs a real novel) walks a book
through the existing `ChapterReader` and ranks names. Over three real novels:

- **`Le Fléau`: all 26 of the top 26 are real named entities** — Stu, Larry, Harold,
  Nick, Frannie, Ralph, Glen, Nadine, Flagg, La Poubelle, Kojak the dog, and `Dieu`,
  which is French for God: a proper noun, always capitalised, and so a correct entry on
  a screen that says NAMES rather than CHARACTERS. **No false positives at all.**
- **`Neuromancien`** returns Case, Molly, Armitage, Maelcum, Riviera, Wintermute,
  Chiba, Tessier-Ashpool — the entire cast.
- **`Darkly Dreaming Dexter`** (English) returns Deborah, Deb, Dexter, LaGuerta,
  Harry, Rita, Dark Passenger, Captain Matthews, Sergeant Doakes. **Not
  French-specific**, which matters because nothing in the rules is vocabulary.

Cost is a scan of text already in RAM: 14,662 blocks, 42,685 sentences, 471,453 words
of `Le Fléau` in **0.5 s on the desktop**, and the walk is one it already does.

**Five rules, each of which replaced something that looked reasonable and was wrong.**
They are in the probe's header with the failure each one fixed; the two worth knowing
before touching it:

- **Sentence-initial suppression is the load-bearing rule.** Rank on mentions that are
  *not* the first word of a sentence. Ranking on total mentions floods the list with
  `Il` / `Je` / `Et` / `Elle` — a French pronoun starts thousands of sentences. One
  rule is the difference between a cast list and a word-frequency table.
- **The introducing sentence is the earliest of the best kind, not the best-scoring.**
  A running best that rewards length selects for the most verbose sentence in the
  novel: it replaced *"Harold, un gros garçon de seize ans"* with a ramble. Length is
  a usable proxy over six samples and a trap over nine hundred.

**THE FORENAME PROBLEM IS SOLVED, AND THE FIX WAS NOT THE ONE EXPECTED.** The gap was
that *"Stuart Redman, sans doute l'homme le plus tranquille d'Arnette"* sat filed under
`Redman` while `Stu` — what is actually on the page, 849 times — got a sentence saying
nothing. Two changes closed it, and the smaller-looking one did most of the work:

- **The containment link's ratio guard was removed, and that was the single largest
  improvement in the probe.** The guard stopped `Frannie` linking to `Frannie
  Goldsmith` whenever the full name was a minority of mentions. It existed so `Larry`
  would not be *labelled* "Larry Underwood" — but the label is chosen separately, from
  the most-mentioned member, so the guard was only ever costing a group its
  introduction. **One rule was answering two questions — which member to show, and
  which member to quote — and they have different right answers.** Le Fléau's top 16
  went from ~4 useful introductions to **11**.
- **A prefix rule, guarded twice**, for the nicknames containment cannot reach:
  Stu → Stuart, Fran → Frannie, Deb → Deborah, Dex → Dexter. A plural is not a
  nickname (`Noir → Noirs` and `État → États` were 2 of the first 8 merges), and an
  ambiguous prefix is declined unless one extension dominates 3:1 — `Fran` extends to
  both `Frank` and `Frannie`, and merging Frank into Frannie is worse than leaving a
  nickname unlinked. `Carl ~ Carla, Carley Yates` is still declined, correctly.

**The prefix rule was measured rather than assumed, because its value was not
obvious.** Le Fléau: 7 merges, **2 clearly right** (Stu and Fran — ranks 1 and 4, the
highest-value entities in the book), **2 clearly wrong** (`Brad → Bradenton`,
`Rich → Richardson`), 3 unverifiable. Dexter: 2 merges, both right, none wrong.
Neuromancien: none drawn. **It earns itself because its wins land at the top of the
list and its errors land in the tail** — on entities under 30 mentions, where the cost
is one imperfect sentence rather than a wrong list. `--prefix 0` turns it off, and the
comparison is the evidence.

What the reader now gets, top of `Le Fléau`:

| | |
|---|---|
| Stu | *Stuart Redman, sans doute l'homme le plus tranquille d'Arnette…* |
| Larry | *…il était Larry Underwood, le type du disque.* |
| Nick | *C'est ainsi que Nick Andros, prisonnier du shérif de Shoyo, devenait son adjoint…* |
| Ralph | *C'était l'homme de la radio, Ralph Brentner, qui l'appelait la Zone libre de Boulder.* |
| Nadine | *…elle n'avait cessé d'être Nadine Cross, extérieurement : douce, gentille avec les enfants, excellente institutrice…* |
| Flagg | *Randall Flagg, l'homme noir, marchait le long de la nationale 51…* |

**THE PRONOUN LEAK WAS NEVER LEXICAL, and that is the most useful thing the probe
taught.** `Il` and `Elle` ranked 7th and 8th on a short book, and the obvious
diagnosis — that telling a pronoun from a name needs a stopword list, and therefore a
per-language dictionary — was **wrong**. A pronoun can only rank at all if it appears
mid-sentence with a capital, so every one of its mentions was a sentence boundary the
probe had *missed*. Printing the preceding 46 bytes (`--why Il`) showed it in one
screen: every case ended in a closing guillemet. Two positional causes, no vocabulary:

- **NBSP is whitespace for splitting.** French typography sets a non-breaking space
  inside guillemets and before `!` `?` `:`, so a quoted sentence really reads
  `« Bonjour ! »`. Skipping only ASCII spaces meant the splitter stopped on the
  NBSP, never reached the closing guillemet and never split — so the *next* sentence's
  opening word counted as mid-sentence. Fixing it found **268 more sentences in
  Neuromancien and 163 in `Le Fléau`**, and removed `Il` and `Elle` from Neuromancien
  entirely. `Le Finlandais` lost its spurious `Le` alias at the same time.
- **A word opening reported speech is sentence-initial wherever it sits.**
  `Elle disait : « Je n'arrive pas à respirer »` puts `Je` mid-sentence by position and
  first-word by grammar. Only a quote or a colon counts — deliberately *not* a dash or
  a paren, since French sets parenthetical em-dashes mid-sentence and suppressing a
  real name there could push it under the threshold.

`Je` and `Tu` are gone; `Il` fell to **rank 57 with 27 mentions**. The top twelve moved
by 2–4 mentions each and did not reorder, so nothing real was suppressed. **The lesson
is the shape: a false positive that looks like it needs a dictionary may be a
punctuation bug wearing a linguistic disguise, and the way to tell is to print the
context rather than reason about the category.**

**One thing is still wrong and 3E inherits it**: alias lists get too long for a 480px
row — *"Stu (Stuart/Stu Redman/Redman/Stuart
Redman)"* — which is a display problem, not a detection one.

**And one negative result worth keeping, because it is the first thing anyone will
try: EXCLUDING `Heading` BLOCKS DOES NOTHING.** The book's own title was ranking and
folding into the character sharing its name, and chapter titles looked like the cause.
They are not: **two of three real EPUBs contain no `h1`–`h6` at all** — `Le Fléau` has
0 of 14,662 blocks, Dexter 0 — and the third's 32 of 3,241 changed the list not at all,
identical rows and identical sentences with counts moving by one. Real books put
chapter titles in `<p class="…">`, which `document.h` correctly calls a Paragraph.

What works is measuring **where a run sits** rather than what tag it wore. A running
header appears in the **first block of every chapter file**; real characters spend
0–7% of their mentions opening a chapter, and a title run is far above that. A 50% cut,
applied per run and *before* grouping (the title dilutes the group it folds into —
Dexter's reads 29% with it and 18% without), **removes exactly one run across the three
books — `Darkly Dreaming Dexter` — and leaves the other two byte-identical in their
top 40.** `--frontcut 0` turns it off, and the `f` column reports the percentage.

**One thing found in passing, and it is not about names:** `Epub::open` refuses a real
Calibre-produced EPUB — `1984 - George Orwell.epub` fails with *"the OPF's
unique-identifier names an id no dc:identifier carries"*. Worth its own look, since
that is a book a user would expect to read.

## Known follow-ups carried out of Phase 1

Found by the Phase 1 review, deliberately deferred. Fold these into Phase 2's
plan rather than rediscovering them:

- **Missing glyphs render as nothing.** `measure()`/`drawText()` skip any
  codepoint absent from a font (`if (!g) continue`), and neither bundled TTF
  contains U+FFFD, so malformed or out-of-subset text is silently invisible
  rather than showing a tofu box. Matters most in Phase 3 when real EPUB text
  arrives. Fix by synthesising a fallback box glyph in `fontc.py`, or falling
  back to a `.notdef`/`?` glyph in `drawText`.
- **`QuietTheme::textInverted` allocates a full-screen scratch framebuffer
  (48 KB) per call and scans every pixel.** Fine for one Home render; wrong
  once lists draw several inverted rows. Phase 2 should invert in place over
  the target rectangle.
- **Peak render heap is ~139 KB** (SDK buffer + portrait + landscape). Phase 2
  can drop it to ~96 KB by rotating directly into the SDK's framebuffer
  instead of allocating `landscape`.
- **`theme_quiet.cpp` layout has unguarded magic numbers**: fixed hint-bar slot
  x-positions with no measurement, a `kMargin + 90` assumption for the page
  string, and no clamp on `menuTop` for long menus. Phase 2's component kit
  should measure and lay out instead.
- **`Font::measure` and `drawText` carry duplicate pen/kerning loops.** Right
  alignment depends on them agreeing; nothing asserts it. Deduplicate when
  Phase 2 adds wrapping.
- **`platformio.ini` declares 16 MB flash with no partition table**, so the app
  is capped at the default ~1.3 MB. Phase 2 or 4 should add one.
- **Flashing to hardware is unverified.** Phase 2's first task should be an
  on-device bring-up: confirm rotation direction (`rotate90CW` vs `CCW`), panel
  polarity (may need `setInverted(true)`), and the SPI pin map.

## Findings from the first on-device bring-up (2026-08-20, Xteink X3)

Encre now renders Home on real hardware. What that session taught us, for
Phase 2 to act on:

- **Device identification is mandatory before touching the display.** One
  binary drives both models, and the X3's panel controller varies by production
  batch (UC8253 vs UC8279d). The SDK's `XteinkDetect` does the work: I2C
  fingerprint for X3-vs-X4, board-profile select, then a display-bus probe that
  promotes the profile to `XteinkX3Uc8279`. Skipping the probe drove a UC8279
  unit with the UC8253 driver: the power-on handshake succeeded and the refresh
  wait then died at its full 30-second timeout. `SPI.begin` with MISO and a
  post-`begin()` `requestResync()` are also required.
- **Rotation is CCW**, measured. CW renders 180° out. Unverified on X4.
- **Type is visibly too small on device, and it is NOT pixel density.** The X4
  is 800×480 at 4.26" (219 PPI) and the X3's 792×528 sits in the same
  ~220–235 PPI band; both board profiles leave `uiScale` at 1.0, and every
  profile that raises it to 1.2 does so for *touch* target size, never density.
  The causes, largest first:
  1. No type ramp — one 16px face draws everything, where the design wants
     ~24px titles and 12–14px chrome.
  2. Layout constants pinned to a 480-wide canvas, so the X3's 528-wide panel
     leaves ~9% of its width unused with content hugging the left edge.
  3. Density: negligible between these two devices.
- **Therefore: do not invent a DPI-scaling formula.** The SDK explicitly warns
  that PPI alone cannot decide UI scale and hand-tunes per board. Phase 2
  should instead (a) make layout measured and proportional rather than pinned
  to constants, and (b) honour `BoardConfig::ACTIVE.uiScale` where it is not
  1.0, which is what a touch board would need.
- **Font-format constraint to design around:** `.rfnt` glyphs are pre-rendered
  bitmaps, so every distinct pixel size needs its own asset. A type ramp times
  scale variants multiplies assets — define the ramp as a fixed set and have
  the theme pick the nearest available size.
- **Second golden set needed** at 528×792 for the X3, alongside the X4's
  480×800.


## Course correction: chrome must be anti-aliased (2026-08-20)

Phase 2A shipped Home at design fidelity in the simulator, and on real X3
hardware **the chrome text was illegible**. The cause is not size.

CrossPoint, which works well on this exact hardware, ships its UI chrome at
`UI_FONT_SIZES=(10 12)` — *smaller* than our 12/13/14 ramp — and its reading
faces at 12/14/16/18. The difference is that it converts glyphs with
`FT_LOAD_RENDER` and `--2bit`: **anti-aliased, 4-level glyphs**. Encre
hard-thresholds to 1 bit. At 12px a stem is 1–1.5px, so anti-aliasing is what
lets the eye reconstruct the letterform; thresholding either drops it or leaves
a jagged single-pixel stroke.

An earlier comparison sheet rendered on a monitor suggested 1-bit chrome looked
crisper than anti-aliased chrome, and Phase 2A was built on that conclusion. It
was wrong: a monitor at 4x zoom is not a 220 PPI panel at reading distance. The
device overrules the sheet.

**Decision:** move chrome (and later body text) to the panel's 2-bit, 4-level
grayscale path — the same approach CrossPoint uses, via the SDK's dual-plane
`copyGrayscaleBuffers` / `writeGrayscalePlaneStrip` API. This is a rendering
pipeline change, not a tweak, and gets its own phase (2A-2) before 2B.

**Memory: resolved by the architecture, not by streaming.** The obvious design
— a 2bpp framebuffer — does not fit: at 528x792 that is 104,544 bytes, and a
portrait plus landscape buffer plus the controller's planes is ~313 KB against
327 KB with ~74 KB already static. CrossPoint's actual approach avoids it
entirely: **keep the framebuffer 1-bit and draw the screen once per bit-plane**
(`storeBwBuffer` -> LSB pass -> `copyGrayscaleLsbBuffers` -> MSB pass ->
`copyGrayscaleMsbBuffers` -> `displayGrayBuffer`). Cost is three 1-bit frames
(~157 KB) rather than a doubling, so `writeGrayscalePlaneStrip` is not needed.

**Do not change the type ramp yet.** With anti-aliasing, 12/13/14 sits inside
CrossPoint's proven range, so the ramp may need no change at all. Re-test on
device after grayscale lands, and only then — if it is still too small — change
the design boards first, per the design-first rule.

**Also decided:** the design boards stay one-per-screen rather than one per
device. The frame becomes a parameter so each board renders at both 480x800 and
528x792, and `make compare` pairs each geometry with its own firmware render.
Duplicating boards would double a 47-board canvas, guarantee drift, and remove
the pressure to keep layouts adaptive. This also closes a real gap: X3 fidelity
is currently unverifiable because the tool only renders one geometry.

## Open questions from the pt-ramp propagation (2026-08-20)

Raised while converting all 34 device boards to the pt-at-150-DPI ramp. Each is
a real design decision, deliberately not settled unilaterally:

- **Articles: 5 rows at 12pt vs 4 rows at 14pt.** Five article rows with
  two-line titles do not fit at 14pt even with spacing at its floor. Resolved
  for now as 5 rows at 12pt (25px) — still inside CrossPoint's proven 10–12pt
  chrome range, and on a reader showing more of the queue beats marginally
  larger type. `InstapaperConnect`'s numbered steps took the same step-down.
  Revisit if 12pt proves hard to read on the panel.
- **Reader body text may be under-sized by its own spec.** The Typography board
  states "Size 18 PT", which at 150 DPI is 37.5px; the boards currently render
  book text at 32px (the ×1.75 scale). If the pt convention applies to book text
  as it does to chrome, the reader wants ~38px, at the cost of a line per page.
  Phase 3 owns body text — decide there, on the panel, not on a monitor.
- **Justified reader text shows rivers at 32px in a ~400px measure.** Inherent
  to a narrow panel at a legible size. The only real fix is hyphenation, which
  is a Phase 3 feature commitment rather than a layout tweak.
- **Display numerals are inconsistent across boards.** Home caps its percent at
  32pt (`--t-display`); other big numerals (Boot's wordmark, Sleep's title) were
  scaled ×1.75 and are literals. Either
  `--t-display` is the token for that role everywhere or the scale is — pick one
  when Phase 2C implements those screens.


## What Phase 2A-2 established (2026-08-20)

Durable conclusions, so later phases do not relitigate them:

- **Type is sized in points at 150 DPI**, CrossPoint's convention
  (`ppem = pt * 150 / 72`). The ramp: meta 10pt/21px, label 11pt/23, value
  12pt/25, body 14pt/29, title 20pt/42, display 32pt/67. Below ~10pt is not
  legible on this glass, measured.
- **Chrome is anti-aliased**, 2-bit coverage through the panel's dual-plane
  path. 1-bit thresholding is what made small type illegible, not size alone.
- **Roles name size AND weight.** All eleven (size, weight) pairs the boards use
  are shipped, and `FontSet::load` refuses to bind a role to an asset built at
  a different size or weight — a mis-binding is a boot failure, never a
  silently wrong screen.
- **Icons are generated from the design boards' own SVG** by `tools/iconc.py`,
  read at generation time. It previously held copies and silently swallowed a
  design fix; it now fails loudly on a missing or ambiguous match.
- **Layout derives from the board's box model, never pinned numbers.** Three
  separate defects came from hardcoding a height that the board computes from
  padding plus content plus border: the header band (6px), menu rows (1px per
  row, compounding), and the hint bar. Bar and row heights are now derived and
  returned.
- **Round once.** The battery sat 1.5px low from three truncating divisions
  compounding; tracking drifted ~3px per label from pre-rounding 2.52px to 3.
  Positions accumulate in fixed point and round at the end.
- **Fixes belong in the primitives.** Every one of the eleven defects was found
  on Home and fixed in `components.cpp`/`text.cpp`/`dither.cpp`/the generators,
  so the remaining screens inherit them.
- **Still known-different from the boards:** baselines sit ~0.5-1px high because
  Chrome's `normal` line-height for Space Grotesk is not FreeType's
  hhea-derived one. Closing it means measuring Chrome's real metrics per face.
