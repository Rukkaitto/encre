# E-Reader Firmware V1 — Implementation Roadmap

> **For agentic workers:** This is the phase index, not an executable plan.
> Each phase below gets its own bite-sized plan in `docs/superpowers/plans/`
> when its turn comes (Phase 1's already exists). Execute phases in order —
> each one ends with working, testable software.

**Spec:** `docs/superpowers/specs/2026-08-20-ereader-firmware-v1-design.md`
**Design canvas:** the "E-Reader V1 UI" artifact (39 boards; V1 Screens +
Flows & States pages are the visual contract, theme B2 "Quiet").

## Ground rules for every phase

- The portable core (`core/`) never includes Arduino headers. It builds on
  macOS via CMake and is covered by doctest unit tests + golden-PNG
  visual-regression tests through the simulator.
- Themes render view-models; screens never draw pixels directly (spec §3.3).
- TDD, bite-sized tasks, frequent commits. Firmware builds via PlatformIO
  `[env:xteink]` (one binary, X3+X4).

## Phases

### Phase 1 — Foundation (plan: `2026-08-20-phase1-foundation.md`)
Repo scaffold, freeink-sdk submodule, desktop test harness, 1-bit
framebuffer, bitmap font pipeline (converter + loader + text rendering),
view-model/theme skeleton with a first QuietTheme Home, simulator CLI
rendering PNGs, and firmware that boots on the X4 and shows that Home.
**Exit:** `make test` green on macOS; a photo of the device showing the Home
screen render.

### Phase 2 — UI system & static screens

Split into three plans: the scope below is three independent subsystems with
different risk profiles, and each sub-phase produces working software on its own.

**2A — Design fidelity** — DONE (plan: `2026-08-20-phase2a-design-fidelity.md`)
Outcome: Home matches its board in the simulator on both geometries, and the
component vocabulary exists. Hardware verification failed on legibility, which
triggered the grayscale course correction below — that was the task working as
intended, not the phase failing.
The typography and drawing foundation everything else renders through: text
ink colour and letterspacing, a missing-glyph fallback, the multi-size type
ramp, canvas-agnostic layout, the QuietTheme component primitives (bands,
rows, hint bars, dither, icons), and Home at full design fidelity on both
panel geometries.
**Exit:** `make compare --only home` shows Home matching its board; goldens at
both 480×800 and 528×792; verified on X3 hardware.

**2B — Interaction runtime**
Input dispatch with short/long press, the screen stack, focus navigation, the
e-ink refresh policy (FAST page turns, FULL every N turns and on transitions),
and the power manager with sleep/wake.
**Exit:** navigate between stub screens on device using the buttons; sleep and
wake cleanly.

**2C — The screens**
Library browsing real files over SD, the settings store and screen, Sleep,
SD-missing, and Home's empty and missing-book variants.
**Exit:** `make compare` shows every V1 screen implemented and matching.

### Phase 3 — Reader engine
EPUB container (miniz) + OPF/XHTML parse (expat) into the document model;
TXT importer; layout engine (shaping, kerning, hyphenation, justify);
pagination + SD cache keyed by settings hash; Reader screen, reader menu,
typography panel (live re-paginate), contents, go-to-page, bookmarks, book
details, progress persistence, corrupt-book dialog.
**Exit:** read a real EPUB end-to-end on device; golden layout tests with
known page breaks.

### Phase 4 — Wi-Fi & transfer
Wi-Fi manager (on-demand STA, saved networks in NVS, AP setup hotspot with
QR); join flow (scan list, button keyboard, failure dialog); HTTP server
with drag-and-drop upload page streaming to `/books`; Transfer screen; web
setup page skeleton (Wi-Fi credentials form).
**Exit:** drop an EPUB from a browser onto the device over Wi-Fi.

### Phase 5 — Hardening & release
X3 bring-up (panel select, fuel gauge/RTC), battery states (low banner,
critical shutdown), sleep screens from covers/user images, cache eviction,
error-path sweep against the Flows & States boards, on-device smoke
checklist, README + flashing instructions, v0.1.0 tag.
**Exit:** a week of daily-driver reading without touching a cable.

## Out of scope for all phases (V2 shelf)
Instapaper (cut from V1 2026-08-20 — designs done, see canvas page

## Known follow-ups carried out of Phase 1

Found by the Phase 1 review, deliberately deferred. Fold these into Phase 2's
plan rather than rediscovering them:

- **Missing glyphs render as nothing.** `measure()`/`drawText()` skip any
  codepoint absent from a font (`if (!g) continue`), and neither bundled TTF
  contains U+FFFD, so malformed or out-of-subset text is silently invisible
  rather than showing a tofu box. Matters most in Phase 3 when real EPUB text
  arrives. Fix by synthesising a fallback box glyph in `fontc.py`, or falling
  back to a `.notdef`/`?` glyph in `drawText`.
- **`QuietTheme::textInverted` allocates a full-screen scratch framebuffer
  (48 KB) per call and scans every pixel.** Fine for one Home render; wrong
  once lists draw several inverted rows. Phase 2 should invert in place over
  the target rectangle.
- **Peak render heap is ~139 KB** (SDK buffer + portrait + landscape). Phase 2
  can drop it to ~96 KB by rotating directly into the SDK's framebuffer
  instead of allocating `landscape`.
- **`theme_quiet.cpp` layout has unguarded magic numbers**: fixed hint-bar slot
  x-positions with no measurement, a `kMargin + 90` assumption for the page
  string, and no clamp on `menuTop` for long menus. Phase 2's component kit
  should measure and lay out instead.
- **`Font::measure` and `drawText` carry duplicate pen/kerning loops.** Right
  alignment depends on them agreeing; nothing asserts it. Deduplicate when
  Phase 2 adds wrapping.
- **`platformio.ini` declares 16 MB flash with no partition table**, so the app
  is capped at the default ~1.3 MB. Phase 2 or 4 should add one.
- **Flashing to hardware is unverified.** Phase 2's first task should be an
  on-device bring-up: confirm rotation direction (`rotate90CW` vs `CCW`), panel
  polarity (may need `setInverted(true)`), and the SPI pin map.

## Findings from the first on-device bring-up (2026-08-20, Xteink X3)

Encre now renders Home on real hardware. What that session taught us, for
Phase 2 to act on:

- **Device identification is mandatory before touching the display.** One
  binary drives both models, and the X3's panel controller varies by production
  batch (UC8253 vs UC8279d). The SDK's `XteinkDetect` does the work: I2C
  fingerprint for X3-vs-X4, board-profile select, then a display-bus probe that
  promotes the profile to `XteinkX3Uc8279`. Skipping the probe drove a UC8279
  unit with the UC8253 driver: the power-on handshake succeeded and the refresh
  wait then died at its full 30-second timeout. `SPI.begin` with MISO and a
  post-`begin()` `requestResync()` are also required.
- **Rotation is CCW**, measured. CW renders 180° out. Unverified on X4.
- **Type is visibly too small on device, and it is NOT pixel density.** The X4
  is 800×480 at 4.26" (219 PPI) and the X3's 792×528 sits in the same
  ~220–235 PPI band; both board profiles leave `uiScale` at 1.0, and every
  profile that raises it to 1.2 does so for *touch* target size, never density.
  The causes, largest first:
  1. No type ramp — one 16px face draws everything, where the design wants
     ~24px titles and 12–14px chrome.
  2. Layout constants pinned to a 480-wide canvas, so the X3's 528-wide panel
     leaves ~9% of its width unused with content hugging the left edge.
  3. Density: negligible between these two devices.
- **Therefore: do not invent a DPI-scaling formula.** The SDK explicitly warns
  that PPI alone cannot decide UI scale and hand-tunes per board. Phase 2
  should instead (a) make layout measured and proportional rather than pinned
  to constants, and (b) honour `BoardConfig::ACTIVE.uiScale` where it is not
  1.0, which is what a touch board would need.
- **Font-format constraint to design around:** `.rfnt` glyphs are pre-rendered
  bitmaps, so every distinct pixel size needs its own asset. A type ramp times
  scale variants multiplies assets — define the ramp as a fixed set and have
  the theme pick the nearest available size.
- **Second golden set needed** at 528×792 for the X3, alongside the X4's
  480×800.


## Course correction: chrome must be anti-aliased (2026-08-20)

Phase 2A shipped Home at design fidelity in the simulator, and on real X3
hardware **the chrome text was illegible**. The cause is not size.

CrossPoint, which works well on this exact hardware, ships its UI chrome at
`UI_FONT_SIZES=(10 12)` — *smaller* than our 12/13/14 ramp — and its reading
faces at 12/14/16/18. The difference is that it converts glyphs with
`FT_LOAD_RENDER` and `--2bit`: **anti-aliased, 4-level glyphs**. Encre
hard-thresholds to 1 bit. At 12px a stem is 1–1.5px, so anti-aliasing is what
lets the eye reconstruct the letterform; thresholding either drops it or leaves
a jagged single-pixel stroke.

An earlier comparison sheet rendered on a monitor suggested 1-bit chrome looked
crisper than anti-aliased chrome, and Phase 2A was built on that conclusion. It
was wrong: a monitor at 4x zoom is not a 220 PPI panel at reading distance. The
device overrules the sheet.

**Decision:** move chrome (and later body text) to the panel's 2-bit, 4-level
grayscale path — the same approach CrossPoint uses, via the SDK's dual-plane
`copyGrayscaleBuffers` / `writeGrayscalePlaneStrip` API. This is a rendering
pipeline change, not a tweak, and gets its own phase (2A-2) before 2B.

**Memory constraint that shapes the design:** at 528x792, 2bpp is 104,544 bytes
per buffer. A portrait plus a landscape buffer plus the SDK's two planes would
be ~313 KB against 327 KB total with ~74 KB already static — it does not fit.
The SDK provides `writeGrayscalePlaneStrip` and reports `supportsStripGrayscale()`
precisely for this: render one 2bpp portrait buffer, then rotate and stream
strips into the controller's planes rather than materialising a second full
buffer. CrossPoint's "tiled grayscale reader path" is the same idea.

**Do not change the type ramp yet.** With anti-aliasing, 12/13/14 sits inside
CrossPoint's proven range, so the ramp may need no change at all. Re-test on
device after grayscale lands, and only then — if it is still too small — change
the design boards first, per the design-first rule.

**Also decided:** the design boards stay one-per-screen rather than one per
device. The frame becomes a parameter so each board renders at both 480x800 and
528x792, and `make compare` pairs each geometry with its own firmware render.
Duplicating boards would double a 47-board canvas, guarantee drift, and remove
the pressure to keep layouts adaptive. This also closes a real gap: X3 fidelity
is currently unverifiable because the tool only renders one geometry.
